ER model, keys, and normalization

Mapped to JIIT DBMS Lab synopsis — Gaming Tournament Management System.

Relationship flow

Player → Team → Registration → Tournament → Match → Result

Additional: Tournament → Venue, Tournament → Prize → PrizeDistribution. Mentor is a self-relationship on Player.

Team

  • team_id PK
  • team_name UNIQUE
  • coach_name, founded_year, status

Player

  • player_id PK
  • team_id FK, mentor_id FK (self)
  • email UNIQUE, ingame_id UNIQUE

Tournament

  • tournament_id PK
  • name, game, dates, status
  • CHECK end_date >= start_date

Venue

  • venue_id PK
  • type Offline/Online
  • M:N with Tournament

Registration

  • registration_id PK
  • tournament_id FK, team_id FK
  • UNIQUE(tournament, team)

MatchEvent

  • match_id PK
  • team1_id, team2_id, venue_id FKs
  • CHECK team1_id <> team2_id

Result

  • result_id PK
  • match_id UNIQUE FK
  • winner_team_id FK, scores

Prize / Distribution

  • prize: tournament + position UNIQUE
  • distribution: prize_id UNIQUE FK
  • team_id FK, awarded_date

Normalization (3NF)

  • 1NF: Atomic attributes only; no repeating player lists inside Team.
  • 2NF: Non-key attributes depend on the full primary key (composite keys such as TournamentVenue and UNIQUE(tournament, team) are fully dependent).
  • 3NF: No transitive dependency — team name is not stored on Player; prize amount is not copied onto PrizeDistribution; tournament name is not stored on Match.

Constraints used

  • PRIMARY KEY on every entity
  • FOREIGN KEY with RESTRICT / CASCADE / SET NULL
  • NOT NULL, UNIQUE, CHECK (age, status, scores, dates, distinct teams)
